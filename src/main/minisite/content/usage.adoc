= Usage
:minisite-index: 300
:minisite-index-title: Usage
:minisite-index-icon: play
:minisite-index-description: From a bare Hop project to rendered diagrams, generated docs and a runnable distribution.

This page walks through a real Apache Hop project from scratch and shows the concrete goals you apply
at each step: render diagrams, generate documentation, build a distribution and run it. The
authoritative, per-goal reference (every parameter, its type, its default and its Maven property) is
generated from `plugin.xml` and available in the xref:mojo/hop-maven-plugin.adoc[goal reference
index].

== Getting started: a minimal Hop project

Apache Hop pipelines and workflows are XML files, normally authored in the Hop GUI. A Hop project is
just a folder - by convention pipelines (`.hpl`) and workflows (`.hwf`) live at the project root, the
metadata in `metadata/`, and the project variables in `project-config.json`:

[source,text]
----
demo-hop/
  metadata/                <- database connections, run configurations
  project-config.json      <- config.variables
  my-pipeline.hpl          <- one pipeline (XML)
----

This layout matches the plugin defaults, so `render` works out of the box on any such project. The
plugin only reads the XML files; it does not need the Hop GUI to render or run them.

== Use case 1: render the diagrams in the build

Render every `.hpl`/`.hwf` to SVG (and optionally Mermaid) headlessly, keeping the source-relative
path. This gives a reproducible, always-current picture of your flows on every commit or CI run.

From the shell, on a project with the standard layout:

[source,bash]
----
mvn io.yupiik.hop:hop-maven-plugin:<version>:render
----

Parameters are overridable with the `-Dhop.render.<name>` properties declared in the
xref:mojo/render.adoc[render reference]. For example, to render only SVG into a dedicated folder:

[source,bash]
----
mvn io.yupiik.hop:hop-maven-plugin:<version>:render \
  -Dhop.render.targetFolder=target/hop-diagrams \
  -Dhop.render.formats=SVG
----

To get it on every build, bind the goal in a phase - `process-resources` so the diagrams are
available to later steps (for example to be copied into the generated documentation):

[source,xml]
----
<build>
  <plugins>
    <plugin>
      <groupId>io.yupiik.hop</groupId>
      <artifactId>hop-maven-plugin</artifactId>
      <executions>
        <execution>
          <id>render-diagrams</id>
          <phase>process-resources</phase>
          <goals>
            <goal>render</goal>
          </goals>
          <configuration>
            <sourceFolder>${project.basedir}</sourceFolder>
            <metadataFolder>${project.basedir}/metadata</metadataFolder>
            <configFile>${project.basedir}/project-config.json</configFile>
            <targetFolder>${project.build.directory}/hop-diagrams</targetFolder>
            <formats>
              <format>SVG</format>
            </formats>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>
----

When your flows use transforms not shipped by the base plugin classpath, enable `autoResolve` and the
goal fetches the matching `hop-transform-*`/`hop-action-*` modules with the Maven resolver:

[source,xml]
----
<configuration>
  <autoResolve>true</autoResolve>
</configuration>
----

== Use case 2: generate documentation for every flow

`generate-doc` reuses the same discovery as `render` and writes one page per flow plus an index (and
optionally the diagram images and an `llms.txt` mirror), derived directly from the Hop files:

[source,xml]
----
<execution>
  <id>generate-doc</id>
  <phase>process-resources</phase>
  <goals>
    <goal>generate-doc</goal>
  </goals>
  <configuration>
    <sourceFolder>${project.basedir}</sourceFolder>
    <outputDirectory>${project.build.directory}/generated-site/content/hop</outputDirectory>
    <imageFolder>${project.build.directory}/generated-site/images/diagrams</imageFolder>
    <includeImage>true</includeImage>
  </configuration>
</execution>
----

TIP: point `outputDirectory` at a `src/main/minisite/content/...` folder to feed the generated pages
straight into a yupiik minisite, exactly like the reference pages you are reading now.

=== Enriching the generated pages from `src/main/hop/documentation`

The pages are derived from the Hop files, but the human prose (role/objective, launch snippet, notes)
is yours. By convention `generate-doc` reads a per-artefact AsciiDoc file from `enrichmentLocation`
(default `src/main/hop/documentation/<flowName>.adoc`); inline `<enrichments>` entries fall back or
override it. The index metadata is carried by document attributes:

[source,asciidoc]
----
= T_SYNC_LOAD
:hop-index-role: Phase 2 : extraction partitionnee source.
:hop-index-order: 7

T_SYNC_LOAD est la phase 2 de l'archivage (la copie des donnees de la partition).

== Script de lancement

[source,bash]
.....
hop-run.sh -f utilities/oracle_sync/T_SYNC_LOAD.hpl -r local
.....

== Voir aussi

* link:../design.html[Design]
----

The body keeps the narrative order of the page: the prose before the first `==` becomes the overview,
each `==` section and the launch script are rendered in the order they were written, prose that follows
a heading stays under it, and nested `===` headings are preserved (nothing is re-sorted to the end).
To place one of the generated sections (configuration, steps, flow, diagram) exactly where the thread
needs it, write a reserved heading at that spot:

[source,asciidoc]
----
== :configuration
----

The reserved headings are `:configuration`, `:steps`, `:flow` and `:diagram`. Any generated section
that is not anchored is appended after the doc thread in that canonical order. With an inline
`<enrichments>` entry (no ordered file body) the fixed order Overview, Configuration, Steps, Flow,
Diagram, Script, then the extra sections is used instead.

== Use case 3: bundle a self-contained distribution

`build` takes a stock Hop client zip, enriches it and packages a zip you can ship. It resolves the
version from `versionUrl` (defaults to the Apache downloads) and, from the `baseDirectory` (default
`src/main/hop/distribution`), copies your files on top so they win over the upstream content:

[source,xml]
----
<execution>
  <id>build-hop</id>
  <goals>
    <goal>build</goal>
  </goals>
  <configuration>
    <hopVersion>2.20.0</hopVersion>
    <baseDirectory>${project.basedir}/src/main/hop/distribution</baseDirectory>
    <drivers>
      <driver>com.oracle.database.jdbc:ojdbc11:23.5.0.24.07</driver>
    </drivers>
    <libs>
      <lib>org.jooq:jooq:3.19.0</lib>
    </libs>
    <transforms>
      <transform>com.acme:acme-custom-transform:1.0.0</transform>
    </transforms>
  </configuration>
</execution>
----

The zip is written to `target/<finalName>.zip` and attached to the build by default; override the
classifier with `classifier` and disable packaging or attachment with `packageDistribution`/`attach`.
A later goal in the same reactor can reference it as a distribution.

== Use case 4: run a pipeline or workflow headlessly

`run` resolves a distribution (the one attached by `build`, or a
`groupId:artifactId:version[:type[:classifier]]` coordinate), unpacks it, merges a `repository` folder
on top and executes a pipeline or workflow via `hop-run.sh`/`hop-run.bat`:

[source,xml]
----
<execution>
  <id>run-demo</id>
  <goals>
    <goal>run</goal>
  </goals>
  <configuration>
    <!-- the distribution built by the same reactor -->
    <distribution>${project.groupId}:${project.artifactId}:${project.version}:zip</distribution>
    <repository>${project.basedir}</repository>
    <pipeline>my-pipeline.hpl</pipeline>
    <runConfig>local</runConfig>
    <parameters>
      <pc.env>LOCAL</pc.env>
    </parameters>
  </configuration>
</execution>
----

A headless `hop-run` needs a run configuration Hop can find. Put it in the merged repository under
`config/metadata/pipeline-run-configuration/local.json` (Hop reads `config/metadata`, not `metadata/`)
and reference it with `runConfig=local`.

== Use case 5: run the Hop server and stop it

`server` starts the Hop server in the background for interactive or long-running workloads;
`server-stop` sends the authenticated `/shutdown` request:

[source,xml]
----
<execution>
  <id>start-server</id>
  <goals>
    <goal>server</goal>
  </goals>
  <configuration>
    <distribution>${project.groupId}:${project.artifactId}:${project.version}:zip</distribution>
    <repository>${project.basedir}</repository>
  </configuration>
</execution>
<execution>
  <id>stop-server</id>
  <goals>
    <goal>server-stop</goal>
  </goals>
  <configuration>
    <stopPassword>your-server-password</stopPassword>
  </configuration>
</execution>
----

== Prerequisites and pitfalls

These operational details matter when using the distribution/run/CLI goals; each goal's parameters are
documented in its xref:mojo/hop-maven-plugin.adoc[goal reference].

=== Passing arguments to the wrapped CLIs (`encrypt`, `run`, `gui`, `server`)

Extra launcher arguments must be a list of separate tokens via `<args>`. A single string
`-D...args="-hop supersecret"` becomes one argv element and will not be split:

[source,xml]
----
<args>
  <arg>-hop</arg>
  <arg>supersecret</arg>
</args>
----

For `encrypt` (a typical need when externalizing a configuration), the underlying `hop-encrypt.sh`
expects `hop-encrypt.sh <-hop|-server> <password>` and prints `Encrypted <hash>` on success. Keep
`waitFor=true` (the default) so the exit code and output are captured.

=== Resolving extra transforms/plugins (the "marketplace")

`build` resolves transform/plugin coordinates through the Maven resolver, so the project must declare
the repository that hosts them. Hop artifacts live on the ASF releases repository:

[source,xml]
----
<repositories>
  <repository>
    <id>apache-releases</id>
    <url>https://repository.apache.org/content/repositories/releases</url>
  </repository>
</repositories>
----

Each installed plugin is written under `hop/plugins/<category>/<artifactId>/` (jar + `lib/` deps and a
`META-INF/jandex.idx`). Custom transforms usable by name in a pipeline are then registered by Hop at
run time.

=== Javaagent injection

Javaagent coordinates in `javaagents` are downloaded into `hop/lib` and injected into the JVM launch
of every `hop-*.sh`/`.bat`, in definition order. For example the OpenTelemetry agent:

[source,xml]
----
<javaagents>
  <javaagent>io.opentelemetry.javaagent:opentelemetry-javaagent:2.10.0</javaagent>
</javaagents>
----

You can verify the agent is active from its startup banner in the launcher output, e.g.
`opentelemetry-javaagent - version: 2.10.0`.
