= Usage
:minisite-index: 300
:minisite-index-title: Usage
:minisite-index-icon: play
:minisite-index-description: Run the render goal from the CLI or bind it to the build.

This page shows how to invoke the `render` goal. For the full list of parameters and their defaults,
see the generated xref:mojo/render.adoc[render goal reference].

== Command line

On a project with the standard Hop layout (diagrams at the project root, metadata in `metadata/`,
variables in `project-config.json`) this is enough:

[source,bash]
----
mvn io.yupiik.hop:hop-maven-plugin:<version>:render
----

Everything is usually overridable with the `hop.render.<name>` system properties described in the
parameter reference. For example, to point at a non-standard source folder and metadata folder and
to render both SVG and Mermaid:

[source,bash]
----
mvn io.yupiik.hop:hop-maven-plugin:<version>:render \
  -Dhop.render.sourceFolder=src/main/repositories \
  -Dhop.render.metadataFolder=src/main/repositories/metadata \
  -Dhop.render.configFile=src/main/resources/hosts/local/env-config.json \
  -Dhop.render.formats=SVG,MERMAID
----

When the diagrams use transforms or actions that are not on the plugin classpath, enable the
auto-resolve mode to fetch the matching `hop-transform-*`/`hop-action-*` modules with the Maven
resolver:

[source,bash]
----
mvn io.yupiik.hop:hop-maven-plugin:<version>:render \
  -Dhop.render.autoResolve=true
----

See xref:configuration.adoc[Configuration] for the mapping rules and the related parameters.

== Binding to the build

Declare the plugin and add an execution to run `render` in a phase of your choice, for example
`process-resources` so diagrams are generated early and can be referenced by later steps:

[source,xml]
----
<build>
  <plugins>
    <plugin>
      <groupId>io.yupiik.hop</groupId>
      <artifactId>hop-maven-plugin</artifactId>
      <executions>
        <execution>
          <id>render-diagrams</id>
          <phase>process-resources</phase>
          <goals>
            <goal>render</goal>
          </goals>
          <configuration>
            <!-- override the HOP-standard defaults for a non-standard layout -->
            <sourceFolder>${project.basedir}/src/main/repositories</sourceFolder>
            <metadataFolder>${project.basedir}/src/main/repositories/metadata</metadataFolder>
            <configFile>${project.basedir}/src/main/resources/hosts/local/env-config.json</configFile>
            <formats>
              <format>SVG</format>
              <format>MERMAID</format>
            </formats>
            <targetFolder>${project.build.directory}/hop-diagrams</targetFolder>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>
----

== include/exclude patterns

`includes` and `excludes` take Ant-style globs matched against the source-relative path. For
example, to render only files under `utilities/`:

[source,xml]
----
<includes>
  <include>utilities/**/*.hpl</include>
  <include>utilities/**/*.hwf</include>
</includes>
----

When `includes` is empty every supported file is processed.

## Example: a Hop project with repositories under `src/main`

The sample project used by this documentation keeps its Hop project home under
`src/main/repositories`. Because the plugin defaults are HOP-standard, you customize it via the
plugin configuration as shown above, or via the matching `hop.render.*` properties. The `metadata`
folder is the one passed to the HOP metadata provider, so database connections resolve correctly.

See xref:configuration.adoc[Configuration] for the wiring details.

## Building a custom distribution

The `build` goal downloads the configured Hop client zip, enriches it and packages it back as a zip:

[source,xml]
----
<plugin>
  <groupId>io.yupiik.hop</groupId>
  <artifactId>hop-maven-plugin</artifactId>
  <executions>
    <execution>
      <id>build-hop</id>
      <goals>
        <goal>build</goal>
      </goals>
      <configuration>
        <hopVersion>2.19.0</hopVersion>
        <!-- put overrides/config under src/main/hop/distribution, they win over the distribution -->
        <baseDirectory>${project.basedir}/src/main/hop/distribution</baseDirectory>
        <drivers>
          <driver>com.oracle.database.jdbc:ojdbc11:23.5.0.24.07</driver>
        </drivers>
        <libs>
          <lib>org.apache.hop:hop-core:2.19.0</lib>
        </libs>
      </configuration>
    </execution>
  </executions>
</plugin>
----

The produced zip is attached to the build (classifier configurable with `classifier`). See the generated
xref:build.adoc[build goal reference] for the full parameter list (transforms, marketplace plugins, jar
overrides, javaagent support and the download credentials).

## Running a pipeline or workflow

`run` resolves a distribution (the one built and attached as a zip, or a distribution coordinate),
merges a repository folder and runs `hop-run.sh`:

[source,xml]
----
<execution>
  <id>run</id>
  <goals>
    <goal>run</goal>
  </goals>
  <configuration>
    <!-- use the distribution attached by the build goal of the same reactor -->
    <distribution>${project.groupId}:${project.artifactId}:${project.version}:zip</distribution>
    <repository>${project.basedir}/src/main/repositories</repository>
    <workflow>utilities/oracle_sync/J_SYNC.hwf</workflow>
    <runConfig>local</runConfig>
    <parameters>
      <pc.env>LOCAL</pc.env>
    </parameters>
  </configuration>
</execution>
----

## Running the Hop server and stopping it

`server` starts the Hop server in the background (`waitFor=false` by default). Stop it with
`server-stop`, which reads host/port/auth from `hop-server.xml`:

[source,xml]
----
<execution>
  <id>start-server</id>
  <goals>
    <goal>server</goal>
  </goals>
  <configuration>
    <distribution>${project.groupId}:${project.artifactId}:${project.version}:zip</distribution>
    <repository>${project.basedir}/src/main/repositories</repository>
  </configuration>
</execution>
<execution>
  <id>stop-server</id>
  <goals>
    <goal>server-stop</goal>
  </goals>
  <configuration>
    <stopPassword>your-server-password</stopPassword>
  </configuration>
</execution>
----

`encrypt` and `gui` wrap the `hop-encrypt` / `hop-gui` launchers with the same distribution management
(see their generated goal references).
== Prerequisites and pitfalls

The following operational details matter when using the distribution/run/CLI goals.

=== Passing arguments to the wrapped CLIs (`encrypt`, `run`, `gui`, `server`)

Extra launcher arguments must be provided as a list of separate tokens via `<args>`. A single string
`-D...args="-hop supersecret"` becomes one argv element and will not be split:

[source,xml]
----
<args>
  <arg>-hop</arg>
  <arg>supersecret</arg>
</args>
----

For the `encrypt` goal the underlying `hop-encrypt.sh` expects `hop-encrypt.sh <-hop|-server> <password>`
and prints `Encrypted <hash>` on success. Set `waitFor=true` (the default) so the exit code and output
are captured.

=== Resolving extra transforms/plugins (the "marketplace")

`build` resolves extra transform/plugin coordinates through the Maven resolver, so the project must
declare the repository that hosts them. Hop artifacts live on the ASF releases repository:

[source,xml]
----
<repositories>
  <repository>
    <id>apache-releases</id>
    <url>https://repository.apache.org/content/repositories/releases</url>
  </repository>
</repositories>
----

Each installed plugin is written under `hop/plugins/<category>/<artifactId>/` (jar + `lib/` deps and a
`META-INF/jandex.idx`). Custom transforms usable by name in a pipeline are then registered by Hop at
run time.

=== Javaagent injection

Javaagent coordinates listed in `javaagents` are downloaded into `hop/lib` and injected into the JVM
launch of every `hop-*.sh`/`.bat`, in definition order. For example the OpenTelemetry agent:

[source,xml]
----
<javaagents>
  <javaagent>io.opentelemetry.javaagent:opentelemetry-javaagent:2.10.0</javaagent>
</javaagents>
----

You can verify the agent is active from its startup banner in the launcher output, e.g.
`opentelemetry-javaagent - version: 2.10.0`.

=== Running pipelines unless headless (`run`)

A headless `hop-run` needs a run configuration Hop can find. The `run` goal merges the configured
`repository` onto the unpacked distribution, so place the run configuration under
`config/metadata/pipeline-run-configuration/local.json` (Hop reads `config/metadata`, not
`metadata/`) and reference it with `runConfig=local` (default `local`). Pipelines paths given in
`pipeline`/`workflow` are resolved relative to the merged repository.
